## Context

参见 [proposal.md](./proposal.md) 的问题背景。本仓库使用同一份 `src/styles.css` 服务 popup 和 options 两个 HTML 入口，其中 `html, body, #root` 当前统一设置为 `760×580` 与 `overflow: hidden`。`OptionsApp` 虽然声明最小视口高度，但无法覆盖根节点的固定尺寸和滚动禁用。

首次绑定完成请求由持久化 `BindSessionRecord` 直接组装后交给通用 JSON 客户端。服务端使用共享 `bindCompleteRequestSchema` 校验请求，但校验失败只返回 `invalid_bind_request`，失败字段没有进入安全日志。当前空云端/空本地单元测试和服务端测试均通过，说明 `localNodes: []` 在现有源码协议中合法；因此不得用放宽 schema 或为空数组添加特殊分支来猜测根因。实现必须先覆盖最终序列化与 HTTP 校验边界，并用字段级诊断识别真实环境偏差。

## Goals / Non-Goals

**Goals:**

- 让 popup 和 options 在静态入口加载时就获得互不影响的页面级布局规则，避免运行时样式闪烁。
- 让 options 外层画布占满视口，并以单一、可预测的纵向滚动路径访问全部设置内容。
- 把绑定完成请求的投影、默认值处理和共享 schema 校验集中在一个边界，保证实际发送的 JSON 与服务端契约一致。
- 在不记录请求值或凭据的前提下，让服务端日志指出无效请求的字段路径和校验类别。
- 用跨序列化与 HTTP 路由的回归测试证明空数据首次初始化可成功完成。

**Non-Goals:**

- 不重新设计设置页的信息架构、视觉主题或现有设置组件。
- 不改变备份下载、备份凭证、版本锁和幂等操作 ID 的安全顺序。
- 不放宽节点、URL、修订号或同步 epoch 的协议约束。
- 不迁移 IndexedDB schema，也不改变现有绑定或收藏数据格式。

## Decisions

### 1. 使用静态页面标识隔离根布局

在 `index.html` 与 `options.html` 的根元素上写入不同的 `data-page` 标识，并在基础样式层按该标识设置页面尺寸：popup 分支保留 `760×580` 和内部滚动模型；options 分支使用 `width: 100%`、`min-height: 100%`，允许纵向溢出。静态标识在 CSS 首次解析前已经存在，不依赖 React effect 或入口脚本修改 class。

`OptionsApp` 保留全视口背景，但移除会形成固定卡片视窗或裁剪内容的约束。设置内容使用响应式水平留白和可读的最大内容宽度；这是内容排版上限，而不是页面根宽度。内容变高时由页面滚动，`SettingsView` 不再依赖一个由 popup 高度驱动的嵌套滚动区。

备选方案是拆分两份完整 CSS。它能做到物理隔离，但会复制主题 token、基础控件和滚动条规则，增加维护成本。另一个方案是只把固定尺寸移动到 `App` 容器；这无法在 React 挂载前建立正确的 popup 根尺寸，也更容易留下 body 溢出差异。

### 2. 绑定完成请求必须先投影再校验

新增单一请求构造边界，输入为持久化绑定会话、策略和幂等操作 ID，输出为共享协议解析器校验后的 `BindCompleteRequest`。构造器显式投影本地节点为创建输入字段，而不是把包含服务端版本、删除状态等额外字段的 `SyncNode[]` 直接作为请求正文；空快照明确投影为合法的空数组。最终解析结果才交给 `SyncClient.bindComplete` 序列化。

若本地构造失败，转换为专门的客户端错误：说明首次绑定数据与协议不一致、请求未发送，并要求用户重新开始绑定。不得把 schema 原始字段值、节点正文或 token 放进 UI。此边界同时给单元测试一个可直接检查“最终发送形状”的稳定接口。

备选方案是仅在 `initialize_cloud` 中硬编码 `localNodes: []`。现有 schema 已接受空数组，该方案无法解释或修复其他缺失字段。放宽服务端 schema 也被否决，因为它会把不完整的版本条件带入写事务。

### 3. 服务端记录结构化校验问题而不记录请求值

绑定完成路由直接保留共享 schema 的校验结果。失败时继续对客户端返回 HTTP 400 与稳定的 `invalid_bind_request`，同时通过现有 logger 写入结构化 warn：事件名、路由、每个 issue 的字段路径和校验代码。日志字段不得包含请求 body、authorization、bind token、节点标题或 URL；现有 logger 的 redact 作为第二层保护，但调用点本身仍只传元数据。

客户端若已经通过同一 schema 校验却收到该错误，将其解释为客户端/服务端协议或部署版本不一致，提示重新连接并确认服务已更新，而不是显示英文服务端原文。

### 4. 回归测试覆盖最终边界并保留根因门槛

布局测试分别断言两个 HTML 入口的页面标识、popup 固定尺寸规则和 options 全视口/可滚动规则；组件测试使用高内容场景验证设置页没有裁剪容器。

绑定测试分三层：请求构造器验证空会话得到可解析的精确正文；客户端测试检查 `JSON.stringify` 后的 body；服务端 HTTP 集成测试完成 bind start、空 cloud snapshot、backup proof 和 empty `initialize_cloud`，并验证最终设备会话与空快照。无效正文测试捕获 logger 输出，只允许字段路径和 issue code 出现。

如果新的完整链路在当前源码仍然通过，实现阶段不得继续猜测 schema 修改；应使用新增日志对照失败环境，确认是字段生产差异还是服务端未部署同一协议版本，再只修正已确认的边界或部署步骤。

## Risks / Trade-offs

- [页面级滚动与组件内部滚动同时存在，可能形成双滚动条] → options 入口只保留页面纵向滚动；popup 继续使用组件内部滚动，并为两种入口分别做视口测试。
- [字段投影遗漏未来新增的节点创建字段] → 构造器必须通过共享 schema，并在协议字段变化时由类型检查与请求快照测试同时失败。
- [服务端诊断日志意外包含敏感值] → 只记录 Zod issue 的 path/code 等元数据，增加日志捕获测试，并继续经过 logger redact。
- [真实错误来自旧服务容器而非当前源码] → 部署时同时重建扩展和服务端，使用发现端点和新增诊断确认版本兼容；不通过放宽 schema 掩盖版本偏差。

## Migration Plan

1. 先提交回归测试与安全诊断，使失败环境能指出协议字段路径。
2. 应用页面入口标识和布局隔离，验证 popup 与 options 构建产物。
3. 应用绑定请求构造/预校验边界，并运行客户端、协议包和服务端测试。
4. 从同一仓库版本重新构建扩展与服务端容器；先更新服务端，再加载新扩展并执行空数据首次绑定验收。
5. 若需要回滚，恢复旧扩展静态资源和服务端镜像即可；本变更无数据迁移，已有 IndexedDB 与 PostgreSQL 数据保持兼容。
